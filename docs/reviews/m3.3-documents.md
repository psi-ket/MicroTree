# M3.3 — Scientific PDF intelligence, full-text extraction and hybrid retrieval

This file has two parts. Part 1 is the assessment and plan, written after the
repository inspection and before any code was changed. Part 2 is the
engineering report, added at the end.

## Part 1 — Assessment and plan (2026-11-03)

### 1. Architecture assessment

What exists and what M3.3 reuses (verified in code):

| Area | Finding | Use in M3.3 |
| --- | --- | --- |
| Works | `scholarly_works` holds the M3.1 `ScholarlyWork` (title, authors, year, venue, DOI, arXiv ID, type) with user corrections applied to derived columns. | Search results show work metadata from here. Filters by author, year, venue and type join on it. Nothing is copied. |
| Items | `library_items` (one per work), `library_collection_items`, archive flag. | Collection filters, "entire library" scope. |
| PDFs | `library_attachments` rows over the content-addressed store `objects/<ab>/<cd>/<sha256>.pdf`. `AttachmentService.readBytes(id)` reads an object by attachment ID; the store refuses links and malformed keys. | The ingestion pipeline reads PDFs only through this service. No second store. Extractions are keyed by attachment ID and record its SHA-256. |
| PDF parsing | pdf.js in a worker thread (256 MB heap, 20 s) validates every PDF at import. | Already validated files are re-checked cheaply (signature, size, page count) before extraction. |
| Jobs | `ImportJobRunner` (in memory, ≤ 2, events) plus `library_import_jobs` rows that become `interrupted` at restart. | Not reused for ingestion: M3.3 jobs must **resume** after restart and carry stages, so they get their own table and queue, following the same event pattern. |
| Runtime | Fastify on loopback, bearer sessions, Origin and Host checks, Zod `parse()`, `StudioError` mapping, `AuditService`, `EventBus` → WebSocket. | All new routes sit inside the authenticated `/api/v1` scope and use the same helpers. |
| Models | `ai-core` `ModelProvider` is a chat interface; `model-adapters/ollama.ts` speaks `/api/chat` and `/api/tags`. | Embeddings get a separate `EmbeddingProvider` interface in `research-retrieval`; it does not import the chat stack. |
| Web | `PdfViewer` dialog (pdf.js, lazy pages, zoom), `ItemDetails`, `LibraryScreen` tabs (Overview, Papers, Collections, Import). | The viewer gains `initialPage` and highlight overlays. The library gains **Search** and **Full text** tabs, and paper details gain a **Full text** view. |
| XML | `literature-engine` has a strict Atom reader that rejects DTDs. | TEI needs mixed content, `xml:id`, larger size and node limits, so `paper-ingestion` gets its own hardened reader built the same way. |
| SQLite | `better-sqlite3` bundles SQLite 3.53 with FTS5 (checked: `unicode61` keeps `ψ`, `H_2` and hyphenated tokens with `tokenchars '-_'`). | Keyword retrieval uses FTS5 in the same database. |

New packages and the dependency direction:

```
document-intelligence (pure, isomorphic: model, coordinates, sentences, text normalisation)
   ▲            ▲                          ▲
   │            │                          └── web (coordinate transforms for highlights)
paper-ingestion │  (GROBID client, TEI parser, PyMuPDF worker, normalisers, pipeline, document store)
   ▲            │
   │      research-retrieval (chunking, embeddings, FTS, vectors, RRF, query, metrics)
   │            ▲
   └── runtime ─┘  services/document-runtime.ts, routes-documents.ts
```

`paper-ingestion` knows nothing about the UI or retrieval. `research-retrieval`
knows nothing about GROBID, the library or literature providers: the runtime
resolves library filters (collection, author, year, venue, type) into a set of
extraction IDs and passes them in.

### 2. Document extraction design

1. **Validate** the attachment bytes again (signature, trailer, size limit,
   page-count limit from PyMuPDF or pdf.js metadata).
2. **Extract with GROBID** (`processFulltextDocument`, TEI with coordinates).
   The raw TEI is kept gzip-compressed in `document_raw_outputs`.
3. **Inspect with PyMuPDF** (subprocess): page geometry (MediaBox, CropBox,
   rotation), words and blocks with coordinates, text per page. Used to fill
   page dimensions, to check that GROBID found the document's text (coverage
   ratio as a quality indicator), and as the fallback extractor.
4. **Normalise** into the extractor-independent model in
   `document-intelligence` (`NormalizedDocument`: metadata, sections, blocks,
   sentences, elements, references, pages, quality, warnings).
5. **Segment** blocks into passages (section aware, §6).
6. **Index** passages in FTS5, then embeddings and vectors if an embedding
   provider is configured.
7. **Activate** the new extraction in one transaction, then delete the
   previous one (and its index rows).

### 4. GROBID integration design (checked against the GROBID service and coordinate documentation, 0.9.x)

- Endpoint from `RS_GROBID_URL` (default `http://127.0.0.1:8070`), never from
  the browser. A non-loopback host is refused unless the operator sets
  `RS_GROBID_ALLOW_REMOTE=1`; then the status panel warns that PDFs leave the
  machine.
- Health: `GET /api/isalive` (`true`/`false`, 503 while initialising) and
  `GET /api/version` (plain text or JSON, both read).
- Request: multipart `input`, `consolidateHeader=0` (its default is `1`, which
  calls external services), `consolidateCitations=0`, `consolidateFunders=0`,
  `includeRawCitations=1`, `segmentSentences=1`, `teiCoordinates` for
  `head`, `p`, `s`, `figure`, `formula`, `ref`, `biblStruct`, `note`, `title`,
  `persName`. Consolidation can be turned on only through
  `RS_GROBID_CONSOLIDATION`, separately.
- Responses: 200 TEI; 204 no content (permanent `empty`); 400 (permanent
  `unsupported`); 500 (permanent `extractor-error`, with GROBID's message
  shortened); 503 busy (retry after 5 to 10 s as documented, at most 3 times);
  timeouts and refused connections (`unavailable`, retried with backoff).
- Bounded concurrency (semaphore, `RS_INGESTION_CONCURRENCY`, default 2) and
  cancellation through `AbortSignal`.
- Coordinates: `coords="p,x,y,w,h;…"`, page 1-based, PDF units, origin top
  left of the CropBox; page sizes from `<facsimile><surface lrx lry>`.

### 5. PDF fallback strategy (PyMuPDF)

- A Python script shipped in the package (`pymupdf-worker.py`) runs with
  `python3 -I` (isolated: no user site, no `PYTHON*` variables, script folder
  not on the path), `shell: false`, an allowlisted environment, a timeout,
  an output cap and (POSIX) an address-space limit. The PDF arrives on stdin;
  JSON leaves on stdout. Nothing is written to disk.
- It reports MediaBox, CropBox, rotation, page size, blocks, lines and words
  with coordinates (PyMuPDF's: CropBox-relative, top-left origin, unrotated
  frame; verified with PyMuPDF 1.26/2.1).
- Priority: GROBID structure when it succeeds; PyMuPDF geometry for page
  dimensions, rotation and coverage checks; PyMuPDF text as the fallback when
  GROBID is unavailable, fails permanently or returns no usable body.
- Reading order for the fallback: per page, drop repeated header and footer
  lines (same text near the top or bottom on most pages), detect columns from
  block x-positions (a gap near the middle crossed by no block), then read
  column by column, top to bottom. Full-width blocks stay in place. Limits are
  documented: no math layout, no table structure, headings guessed from font
  size and bold flags only.
- **needs_ocr**: when neither extractor finds text and PyMuPDF reports pages
  with images but (almost) no characters. A PDF with no text and no images is
  `failed` (`empty`), not "scanned". Nothing is invented.
- If Python or PyMuPDF is missing, the fallback is reported unavailable.

### 6. Passage and chunking strategy

- Token counts are estimated (words × 1.3, and every symbol run counted) so no
  tokenizer is needed; the estimate is conservative against the embedding
  limit.
- Defaults: target 550, maximum 700, overlap 75 tokens, all configurable and
  recorded in the extraction's configuration.
- Paragraphs accumulate in order **within one section** until the target.
  A paragraph over the maximum is split at sentence boundaries with overlap of
  whole sentences. Section boundaries are never crossed; each passage stores
  its section path and its text is indexed with the heading.
- Display formulas, figure captions and table captions become their own
  passages (`kind` `formula` or `caption`); the abstract is its own kind;
  references are `kind: reference` and excluded from body retrieval unless
  asked for.
- Identity: `id` is unique per extraction; `stable_key = sha256(source sha,
  section path, text hash, occurrence)` lets a reprocessed document keep
  the same key for unchanged passages; `text_hash` drives the embedding cache.

### 7. Embedding architecture

- `EmbeddingProvider { id, getModelInfo(), embed(texts, signal) }` in
  `research-retrieval/providers`, separate from `ai-core`.
- `OllamaEmbeddingProvider`: `POST /api/embed` with batches (`input` array),
  model availability and digest from `GET /api/tags` (digest = model version),
  dimension check on every vector, finite-number check, timeout, retries for
  network errors and 5xx, cancellation.
- The provider is configured in settings (`retrieval` scope: model, base URL).
  Base URLs must be loopback unless `RS_EMBEDDINGS_ALLOW_REMOTE=1`. No hosted
  provider is enabled in M3.3; the interface carries a `local: boolean` flag
  and the runtime refuses non-local providers without a recorded consent.
- An embedding space is (provider, model, dimensions, version). Changing the
  model creates a new space and requires an explicit reindex; the old space
  stays searchable until the new one is complete and activated. Queries are
  embedded in the active space only.

### 8. Vector storage decision

SQLite BLOBs of unit-normalised float32 vectors, scanned in Node with a dot
product (cosine), filtered by extraction IDs before scoring.

Considered `sqlite-vec` (a loadable extension): it needs a native binary per
platform loaded into `better-sqlite3`, which the build and Windows support do
not have today, and it is pre-1.0. A separate vector service would add a
process to manage. For a personal library (tens of thousands of passages) a
scan is fast enough (benchmarked in the report) and persists with the rest of
the data. `VectorStore` is an interface, so an ANN backend can replace it
without touching callers.

### 9. Hybrid ranking strategy

- Keyword: FTS5 `bm25()` over normalised text with the original query parsed
  into phrases, terms, `AND`/`OR`/`NOT` and field filters; DOI and arXiv
  queries are matched as identifiers (works and extracted references).
- Semantic: cosine over the active space.
- Hybrid: Reciprocal Rank Fusion, `score = Σ wᵢ / (k + rankᵢ)`, `k = 60`,
  weights 1 and 1 by default, each list cut at 100. Component ranks are kept;
  `matchedBy` says which lists found the passage. The score is a rank-fusion
  number, not a probability, and the UI says so.
- Ties are broken by keyword rank, then passage ID, so results are
  reproducible.

### 10. Security review

| Threat | Control |
| --- | --- |
| XXE, billion laughs | Own TEI reader: `<!DOCTYPE` and `<!ENTITY` refused, only predefined and numeric entities, size (32 MB), depth (256) and node (2 M) limits. |
| Hostile PDFs | Already validated at import; re-checked; PyMuPDF in an isolated subprocess with timeout, memory and output caps; GROBID in its own process. No content is executed. |
| Resource exhaustion | File size and page limits, per-stage timeouts, bounded concurrency, capped TEI and JSON sizes, passage and element count caps. |
| SSRF | GROBID URL from the environment only; embedding URL loopback unless the operator allows remote; no URL from documents is ever fetched. |
| Paths | Workers receive bytes on stdin, not paths; the API returns IDs only; no temporary files. |
| Extracted HTML or script | Extracted text is rendered as React text only; TEI markup is never rendered. |
| Prompt injection | Passages are data. Nothing in M3.3 sends them to a chat model, and no extracted text drives an action. |
| Data leaving the machine | Remote GROBID or embeddings need an operator switch and show a warning; hosted embeddings are not implemented. |
| Unverified references | References are stored as extracted, with `resolution_status`; links to works use exact DOI or arXiv ID only. |

### 11. UI integration plan

- **Paper details**: a "Full text" panel (status, extractor and version,
  quality indicators, Process/Reprocess) opening a **Full text** dialog with a
  table of contents, sections, paragraphs, figures, tables, equations and
  references; selecting a section opens the PDF at its page.
- **Library → Search**: query box, mode (keyword, semantic, hybrid), scope
  (library, collection, paper), filters (author, years, section type), results
  with paper title, authors, year, venue, section, exact passage, page,
  retrieval method and ranks, link to the source.
- **Source view**: the PDF viewer opens at the page and draws the passage's
  boxes when they exist; neighbouring passages are shown; "Back to results"
  keeps the result list.
- **Library → Full text** dashboard: processed, waiting, failed, needs OCR,
  embedding progress, last indexing time, process all, reprocess, reindex,
  extractor and embedding status with actionable messages.

### 12. Testing strategy

- `document-intelligence`: coordinate conversions (origins, rotation 0/90/180/

  segmentation (abbreviations, decimals, citations, math), normalisation.
- `paper-ingestion`: XML security (XXE, entity bombs, depth), TEI parser on

- `research-retrieval`: chunking rules, FTS (phrases, Boolean, scientific
  terms, identifiers), vector store (dimensions, isolation, deletion), RRF
  arithmetic, filters and pagination, Ollama provider against a mock server,
  evaluation metrics on a small synthetic labelled set.
- Runtime: routes, auth, validation, jobs (dedupe, cancel, resume after
  restart, failed reprocess keeps the old extraction), deletion cascades, no
  paths in responses, mock GROBID and mock Ollama.
- Web: search workspace, full-text view, dashboard, PDF highlight placement;
  axe on each.

No copyrighted papers are added; every fixture is generated or written for the
tests.

## Part 2 — Engineering report (2026-11-03)

### 1. What was built

- **`packages/document-intelligence`**: the extractor-independent model,
  canonical coordinates with explicit conversions (tested against PDF.js on
  rotated and cropped pages), sentence segmentation, search-text
  normalisation, provenance, versioning.
- **`packages/paper-ingestion`**: hardened TEI reader; GROBID client (health,
  version, documented options, consolidation off, retries only for 503,
  timeouts and refused connections, bounded concurrency, cancellation); TEI
  parser and normaliser; PyMuPDF subprocess adapter and layout normaliser
  (geometry, columns, running heads, headings, captions, references, scans);
  document store; persistent job queue with dedupe, cancellation, resume and
  a crash limit.
- **`packages/research-retrieval`**: section-aware segmentation, embedding
  interface and Ollama provider, embedding cache, FTS5 keyword search,
  SQLite vector store, RRF hybrid engine, query parser, metrics and a
  labelled evaluation set.
- **Database**: migration `0003_documents` (12 tables and the FTS5 index)
  with a down script.
- **Runtime**: `DocumentRuntime`, 20 routes, two event types, audit events,
  configuration variables.
- **Web**: Full text panel and view in paper details, Search text workspace,
  source view with highlights, Full text dashboard.

The plan in Part 1 was followed. Deviations: the extraction's reprocess
replaces and then deletes the previous extraction (rather than keeping all
versions), so the database does not grow with every run; the active
extraction is never touched until its replacement is indexed.

### 2. Problems found and fixed during the work

- PDF.js 6 removed `convertToViewportRectangle` and `isEvalSupported`; the
  alignment test uses `convertToViewportPoint`.
- Without stemming, `hamiltonian` did not match `Hamiltonians` nor `code`
  `codes`. The FTS tokenizer now uses Porter stemming; the evaluation shows a
  small recall gain (0.661 → 0.679) with nDCG unchanged.
- GROBID paragraphs often carry boxes only on their sentences; the block
  now uses its sentences' boxes, so its pages are known.
- In the layout fallback, the first large heading on page 1 was taken as the
  title (and a title starting with "A" was read as a section letter); titles
  now must be the largest text on page 1 and not look like a numbered or
  known section heading.
- Stage changes were not published through the queue's callback; each run
  now publishes through its own callback.
- The highlight transform first used the unrotated page size; PDF.js gives
  the displayed size, which is what the transform expects.
- In Chromium, axe found low-contrast page links and accessible names that
  did not contain their visible text; both fixed. The library tabs no longer
  overflow at 390 px.
- The `0002` down-migration test assumed `0002` was the newest migration; it
  now rolls back `0003` first.

### 4. Known limitations

- The layout fallback has no equation or table structure and handles one
  gutter per band; GROBID is needed for scientific structure.
- Whether GROBID reports rotated pages in the displayed frame is detected
  from page sizes; this is tested with synthetic input only.
- Keyword search cannot match symbols that are not tokens (`=`, `∝`).
- The vector search is an exact scan held in memory per space.
- OCR is not performed; scans are reported as needing it.
- No hosted embedding providers, no reranker, no claim extraction (M5).

### 5. Recommendations for M4/M5

- Run the pipeline against a local GROBID 0.9 on a set of openly licensed
  papers (arXiv with CC licences) and record extraction metrics (coverage,
  section and reference counts, coordinate alignment).
- Label a larger retrieval set from those papers and evaluate a real local
  embedding model before relying on semantic ranking.
- Build M5 evidence on `document_sentences`, which already link to passages
  and blocks with boxes where GROBID gave them.
