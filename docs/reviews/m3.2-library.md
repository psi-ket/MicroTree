# M3.2 — Personal research library and reference manager

This file has two parts. Part 1 is the assessment and plan, written before any
code was changed. Part 2 is the engineering report, added at the end.

## Part 1 — Assessment and plan (2026-11-03)

### 1. Existing database and code assessment

**Database** (`packages/database`, one SQLite file, WAL, `foreign_keys = ON`,
drizzle-kit SQL migrations applied at start):

- Core tables: `projects`, `project_files` (index of files on disk),
  `settings` (scope/key JSON), `compilation_jobs`, `audit_events`.
- M3.1 tables: `literature_cache`, `literature_search_history`,
  `literature_provider_state`. **There is no table of works**: a
  `ScholarlyWork` exists only inside cached provider answers, which expire.
  The library therefore needs a durable home for works.
- AI tables live in the same file with their own migration history
  (`packages/ai-storage`, `__ai_migrations`); keys are in the `SecretStore`
  (`@napi-rs/keyring`, file, or memory), never in SQLite.
- Migrations are forward only (drizzle has no down migrations).

**M3.1 engine** (verified in code): `LiteratureService` in the runtime exposes
`search`, `work(id)`, `resolveDoi`, `resolveArxiv`, `related`, `author`. It
returns merged `ScholarlyWork`s with `sourceRecords`, `conflicts`, attributed
citation observations, and canonical IDs `doi:` > `arxiv:` > `openalex:` >
`semantic-scholar:`. Identifier normalisers (`normalizeDoi`,
`parseArxivId`, `interpretQuery`), deduplication and `mergeRecords` are
exported by `@research-studio/literature-engine`; BibTeX writing
(`toBibTeX`, `citationKey`, `escapeBibtex`) by its browser-safe `format`
entry. The library will call these, never a provider directly.

**BibTeX today**: `document-engine/src/bibtex.ts` is a tolerant *scanner*
(key, type, title, author, year) used for `\cite` completion; it ignores
`@string`, concatenation and most fields. `extractCitations` finds cite
keys in `.tex` (any `\…cite…` command). There is no BibTeX import,
merge or field-preserving writer.

**Files**: `ProjectFs` (PathGuard, real-path checks, atomic `writeText` with
compare-and-swap on the content hash) is the only way the runtime writes
project files; `ProjectService.writeFile` audits and publishes
`files.changed`. Uploads (`validateUpload`) sniff magic bytes. Multipart is
registered globally with `files: 1`; routes override limits per request.

**Web**: hash routes chosen in `App.tsx` (`#/`, `#/p/<id>`, `#/literature`);
TanStack Query over the typed client; Monaco with a `DiffEditor` already used
by the AI review and compare dialogs; pdf.js 6 (also loadable in Node, checked:
`pdfjs-dist/legacy/build/pdf.mjs` reads metadata and page text).

### 2. Library data model

One durable **work** row per paper, holding the M3.1 `ScholarlyWork` (with its
source records) as the single copy of bibliographic metadata, and a
**library item** holding only the user's own state.

| Table | Purpose and key columns |
| --- | --- |
| `scholarly_works` | `id` (`wrk_…`), `canonical_id` (M3.1 ID, unique, null for unresolved works), `origin` (`providers`, `bibtex`, `ris`, `pdf`, `manual`, `zotero`), `work` (JSON `ScholarlyWork`), `local_source` (JSON: the imported BibTeX entry, RIS record, Zotero item data or PDF metadata the values came from), `user_edits` (JSON: fields the user corrected, re-applied when the work is refreshed), derived index columns `doi` (unique), `arxiv_id` (unique), `title_key`, `first_author_key`, `year`; timestamps |
| `library_items` | `id`, `scholarly_work_id` (unique FK: one item per work, so duplicates are impossible by construction), `citation_key` (unique, case-insensitive), `reading_status` (`to-read`, `reading`, `read`, `important`), `is_favorite`, `notes`, `metadata_status` (`resolved`, `needs-review`, `unresolved`, `manual`), `match` (JSON: confidence and candidates awaiting a decision), `bibtex_type`, `bibtex_extra` (JSON: fields to keep on export, e.g. unknown fields from an imported `.bib`), `added_at`, `updated_at`, `last_opened_at`, `archived_at` |
| `library_collections` | `id`, `name` (unique, case-insensitive), `description`, `color`, timestamps |
| `library_collection_items` | PK (`collection_id`, `library_item_id`), `added_at`; both FKs cascade |
| `library_tags`, `library_item_tags` | tag `name` unique case-insensitive; PK (`library_item_id`, `tag_id`) |
| `library_attachments` | `id`, `library_item_id` (FK), `file_name`, `original_file_name`, `storage_key`, `mime_type`, `file_size`, `sha256`, `attachment_type` (`pdf`, `supplementary`, `other`), `source` (`upload`, `open-access`, `zotero`), `source_url`, timestamps; unique (`library_item_id`, `sha256`); index on `sha256` |
| `library_external_links` | `id`, `library_item_id`, `provider` (`zotero`), `external_library_id` (`web:users/123`, `local:<server id>:users/0`), `external_item_id`, `external_version`, `last_synced_at`, `sync_status` (`synced`, `local-changes`, `remote-changes`, `conflict`, `error`), `remote_snapshot` (JSON of the last synced remote data, for conflict detection), `conflict` (JSON); unique on (provider, library, external item) and (provider, library, item) |
| `library_external_collections` | Zotero collection ↔ library collection mapping with version |
| `library_project_links` | `id`, `project_id` (FK → `projects`, cascade), `library_item_id` (FK, cascade), `created_at`; unique pair |
| `library_import_jobs` | `id`, `kind`, `status`, counts, `items` (JSON per-file results), `error`, timestamps; running jobs become `interrupted` on start |

The user's corrections live in `user_edits` on the work, so the provider
`sourceRecords` stay untouched (provenance) while the work shows the
corrected value, flagged as edited by the user. `work` is stored as received
and the corrections are applied on read (the derived index columns use the
corrected values), so a correction can be undone and survives a refresh. Preferences (citation-key
format) are in `settings` scope `library`; per-project reference settings
(target `.bib` file, default cite command) in scope `project:<id>`.

### 3. PDF storage

- Location: `<RS_DATA_DIR>/library/objects/<ab>/<cd>/<sha256>.pdf`;
  temporary files in `<RS_DATA_DIR>/library/tmp`. Paths are computed by the
  runtime from the hash only; the browser never sends or sees a path (the API
  returns attachment IDs).
- Import: stream the upload to a temp file (`wx`, owner-only) while hashing
  and counting bytes (limit `RS_LIBRARY_MAX_PDF_BYTES`, default 100 MB);
  validate; `fsync`; rename into place if the object does not exist yet
  (same hash = same bytes, so an existing object is reused and the temp file
  removed); then insert the attachment row in a transaction.
- Ownership: an object is owned by the attachment rows with its hash. Removing
  an attachment deletes the row, then deletes the object only if no row still
  refers to it. Operations on one hash are serialised in-process.
- Recovery (start-up and hourly): empty `tmp`; delete objects no row refers
  to (crash between rename and insert, or between delete and unlink); mark
  rows whose object is missing as `missing` in API responses.
- Validation: `%PDF-` header in the first 1 KiB, `%%EOF` in the last 2 KiB,
  then a parse in a **worker thread** with memory limits and a timeout
  (pdf.js with eval, fonts, XFA and scripting disabled) that must report at
  least one page. Encrypted, malformed or oversized files are refused with a
  reason. PDFs are never executed, never opened by the OS, and are stored
  outside every project. They are served to the app as bytes
  (`Content-Type: application/pdf`, `Content-Disposition: attachment` for
  downloads, sandboxing CSP) and viewed with pdf.js inside the app.
- Open-access download: only URLs that the M3.1 work itself lists
  (`openAccess.pdfUrl`, `urls.pdf`), re-checked server-side; `https` only;
  every redirect re-checked; hosts resolving to loopback, private or
  link-local addresses refused; size and time limits; the result must pass
  the same PDF validation.
- M3.3 can read the same objects by attachment ID; no second document store.

### 4. Metadata resolution and BibTeX integration

**PDF pipeline**: read Info/XMP metadata and the text of the first two pages
(in the worker) → extract DOIs (also `doi.org` URLs, hyphenation across lines
removed) and arXiv IDs (`arXiv:…`, arxiv.org URLs, the arXiv stamp) →
resolve through `LiteratureService.resolveDoi/resolveArxiv` → otherwise
search by title (and first author) → score candidates.

Confidence: `exact-doi`, `exact-arxiv` (identifier found in the PDF and
resolved), `strong` (title nearly identical and first author matches),
`possible`, `unresolved`. Only exact matches are applied automatically. A
`strong` match is pre-selected but needs one click (a bulk "accept strong
matches" action exists); anything weaker lists candidates. Until then the
PDF is kept under an unresolved item whose title is the PDF's own Title
metadata, or the file name, marked as such. Nothing is invented: missing
authors, dates or DOIs stay empty.

**BibTeX**: a full parser in `document-engine` (pure, also usable by the web):
`@string` with concatenation (`#`) and month macros, `@comment`,
`@preamble`, brace and quote values with nesting and escapes, `(`…`)`
entries, recovery to the next `@` with line-numbered errors, raw values kept
next to decoded Unicode values (`{\"o}` → ö). The existing scanner stays for
completion. Import maps known fields to a work (`origin: bibtex`), keeps the
whole entry in `local_source` and unknown fields in `bibtex_extra`; entries
with a DOI or arXiv ID can be resolved through M3.1 when the user asks.
Export uses the effective work plus preserved fields; the writer is the M3.1
`format` module, extended so the library can add fields.

**Citation keys**: formats `author-year`, `author-year-keyword` (M3.1's),
`author-year-title`, or a custom template with tokens (`{author}`,
`{Author}`, `{year}`, `{word}`, `{title}`, …). Keys are assigned once and
stored; collisions get `a`, `b`, … suffixes; uniqueness is enforced by the
database (case-insensitive). A key that appears in any linked project's
`.tex` files or `.bib` file is never changed without an explicit confirmation
that lists where it is used; batch generation only fills missing keys or
keys not used anywhere.

**Project `.bib` sync** (never a blind overwrite): the runtime parses the
project's target `.bib`, compares it with the linked library items, and
proposes changes: add an entry; add missing fields to an entry that is the
same work (custom fields and values untouched); report an entry with the
same DOI under another key (no duplicate added; use that key); report a key
collision with a different work (not applied). The preview returns the old
text, the proposed text and the change list; the user reviews a diff,
deselects changes, and applies. Apply recomputes and writes through
`ProjectService.writeFile` with the previewed file hash, so a file that
changed in between is refused (409) instead of overwritten.

### 5. Zotero integration (verified against zotero.org documentation, 2026-11-03)

- **Web API v3** (`https://api.zotero.org`, `Zotero-API-Version: 3`, key in
  the `Zotero-API-Key` header; user ID from `GET /keys/current`, which
  answers 403 without a key). Reads page with `limit` ≤ 100 and `start`, report
  `Total-Results` and `Last-Modified-Version`, support `since=` for changes.
  Writes: up to 50 objects per `POST`, `Zotero-Write-Token` for idempotent
  creation, `If-Unmodified-Since-Version` / `version` for updates, `412` when
  the item changed remotely. Rate limits: honour `Backoff`, `Retry-After` on
  429/503, at most 4 concurrent requests (we use 1). Files:
  `GET …/items/<key>/file`, checked against the item's `md5`.
- **Local API** (Zotero desktop, `http://localhost:23119/api/`, user `0`,
  enabled in Zotero's Advanced settings). Reads need no key; writes (Zotero
  10+) need a separate key granted through a dialog; versions are local and
  unrelated to web versions, partitioned by `Zotero-Server-ID`; file endpoints
  redirect to a `file://` URL. Because the capabilities differ, M3.2 treats it
  as a **read-only import source** and keeps its links under a separate
  external library ID.
- Scope: connect (key stored in the runtime's secret store as
  `zotero:web`), preview then import items and collections, map external IDs,
  optionally download stored PDF attachments, preview then export selected
  items (create or update), conflict detection on both sides (an item changed
  both remotely and locally since the last sync is marked `conflict` and left
  alone until the user picks a side). No background bidirectional sync.
- The schema (`https://api.zotero.org/schema`, version 42) gives the item
  types and fields mapped (`journalArticle`, `preprint`, `conferencePaper`,
  `book`, `bookSection`, `thesis`, `report`, others as `document`).

### 6. Frontend

- `#/library` with tabs **Overview**, **Papers**, **Collections**, **Import**
  (entry points next to "Literature" in the project list and the workspace
  top bar). Overview: counts, collections, recently added and opened. Papers:
  list and grid, search, filters (collection, tag, status, year, author, PDF),
  sorts, multi-select with bulk collection, tag, status and export actions;
  detail panel with metadata (source and edits marked), abstract, PDFs
  (open in an in-app viewer, download), notes, tags, collections, citation
  key, linked projects, Zotero link, and actions. Collections: list with
  counts; drag papers onto a collection. Import: drop zone for PDFs and
  `.bib`/`.ris` files, DOI/arXiv box, Zotero; jobs with progress, match
  status, duplicate warnings, errors, and the review queue.
- Literature page: **Add to library** on results and details (and "Add with
  PDF" when an open-access PDF is listed).
- Workspace: a **References** panel (toggle like the assistant) to search
  the library, link papers, insert `\cite`-family commands at the cursor,
  list the project's cite keys as resolved / only in `.bib` / unresolved,
  open a key's library record, and review `.bib` updates in a diff.

### 7. Migration strategy

- Core migration `0002_library` in `packages/database` (FKs to `projects`
  need the core schema; one migration history). Additive only: no existing
  table changes, so M0–M3.1 data is untouched.
- A matching hand-written `migrations/down/0002_library.sql` drops the new
  tables; a test applies up, down and up again. It is not run automatically.
- The production build copies migrations as before.

### 8. Testing strategy

- **database**: constraints (duplicate DOI/arXiv/key, one item per work,
  collection membership, tags, attachments, external links, project links,
  cascades), up/down migration.
- **document-engine**: BibTeX parser (strings, concatenation, comments,
  preamble, nesting, escapes, parentheses, Unicode, errors with recovery,
  duplicates).
- **research-library** (no network): RIS import/export, BibTeX import/export
  round trip, citation keys (formats, collisions, protection), identifier
  extraction from real PDF text, PDF validation (valid, wrong type, truncated,
  encrypted, oversized, worker timeout), content-addressed storage (hashing,
  dedup, atomic rename, crash recovery, safe deletion, traversal and link
  attempts), matcher confidence levels, metadata merge and user edits,
  `.bib` merge planning, Zotero client and mapper against recorded
  documentation-shaped responses (paging, versions, 412, 429/Backoff, errors).
- **runtime**: every route against the mock literature server and a mock
  Zotero server; jobs with progress and cancellation; restart persistence.
- **web**: component tests with axe for the library, import center and
  References panel.
- **Playwright**: the full workflow (search → add → PDF → resolve →
  collection → project → `.bib` review → cite → compile → runtime restart →
  still there), against mock providers.
- Live checks stay opt-in; Zotero is tested only with mocks (no account or
  key is used).

Implementation proceeds in stages (schema; BibTeX/RIS/keys; storage and
PDFs; resolution and library service; runtime API and jobs; project
integration; Zotero; web; end to end and docs), each followed by typecheck,
lint and tests.

The plan in Part 1 was followed. Deviations:

- **`.bib` preview of a selection.** The plan had the user "deselect changes"
  on one preview. A diff of *all* changes next to a selection would show text
  that is not written, so `bib/preview` takes `changeIds` and renders only
  those; the dialog re-previews on every change of selection and enables
  "Write" only when the diff shown matches the selection. A test checks that
  the previewed text equals the file written.
- **Not built from the plan**: a bulk "accept strong matches" action, a grid
  view, year/author fields in the filter rail (the API has them), drag and
  drop onto collections (selection actions instead), and "Add with PDF" as a
  separate button (open-access download is a preference and a button on the
  paper).
- **Duplicates UI** was added late (Overview, "Possibly the same paper"):
  the API existed but nothing showed it.

### 5. Recommendations for M3.3

- Read PDFs by attachment ID from the same store (`AttachmentService` and
  `AttachmentStorage.resolve`); do not add a second document store. Run any
  full-text extraction in the same worker model with the same limits.
- Key full-text, chunks and embeddings by `sha256` (shared by identical
  files) and link them to items through `library_attachments`.
- Reuse `library_import_jobs` and `ImportJobRunner` for long ingestion, with
  the same progress events, instead of a new job system.
- Keep the rule that nothing inferred is written into a work: derived data
  (summaries, extracted references) should live beside it with provenance.
- Before M3.3 starts: a live check of Zotero with a throwaway account, and a
  decision on whether `strong` matches should get a bulk accept.
